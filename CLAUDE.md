# CLAUDE.md

Context and rules for any Claude Code instance working in this repo (including parallel worktrees).

## Project idea in one line

The context Claude.ai has should also be available to Claude Code. Everything else (storage, embeddings, MCP, capture) is plumbing to get there.

Full detail in [README.md](README.md) and [ROADMAP.md](ROADMAP.md).

## Working rules (apply ALWAYS)

1. **Read the code before and after editing.** Before so you do not break anything, after to verify what ended up there.
2. **Keep README, ROADMAP, and DEVLOG in sync with every relevant change.** Update them in the same iteration as the code.
3. **Review the code you just wrote for bugs** before closing the task.
4. **When closing each ROADMAP phase, audit the whole project** for bugs, obsolete code, and vulnerabilities. Deliver a written report.
5. **Plan before coding.** No writing code without a clear plan.
6. **If there are real doubts, ask.** Do not assume.
7. **Code and plans designed to scale.** Clear separation of responsibilities (pure core, swappable transport, embedder and storage behind interfaces).
8. **No em dashes as connectors.** Use commas, periods, parentheses. Applies to docs, commits, code, and replies to the user.
9. **No Claude shoutouts in commits.** No `Co-Authored-By`, no AI footers. Commits signed only by the human author.
10. **Apply these rules in every iteration.**

## Stack

- Python 3.12+, package manager [uv](https://docs.astral.sh/uv/).
- [FastMCP](https://github.com/jlowin/fastmcp) for the MCP server (supports stdio and SSE/HTTP).
- SQLite + [sqlite-vec](https://github.com/asg017/sqlite-vec) for storage and vector search.
- [fastembed](https://github.com/qdrant/fastembed) by default (zero-config, embedded ONNX) or optional [Ollama](https://ollama.com) with `nomic-embed-text`. Backend configurable via `MEMEX_EMBED_BACKEND`.
- `pydantic` + `pydantic-settings` for config and models.
- `typer` + `rich` for CLI.
- `pytest`, `ruff`, `mypy` for test/lint/typecheck.

## Multi-Claude with git worktrees

To run several Claudes in parallel on independent tasks:

```bash
git worktree add ../Memex-ingest feature/ingest
git worktree add ../Memex-embed  feature/embeddings
git worktree add ../Memex-store  feature/storage
```

Each worktree is a separate folder with its own branch and its own `.venv` (uv isolates on its own). They converge to the same `.git`. Each Claude works without stepping on files, and at merge time all changes land in the same repo.

**Limits:** worktrees do not see each other until merge. Better to split by independent module, not by cross-cutting feature. The coordinator is the human (or a "lead" Claude on `main`).

### File-based sync (dual-boot): a new transport over the SAME core, plus its own input-trust seam (2026-06-30)
- **The sync core was already transport-agnostic, so file sync is a new transport, not a parallel implementation.** `records.select_reconcile` (LWW diff), `records.serialize_conversation`/`insert_record` (wire format + consistent insert), and `records.local_manifest` know nothing about HTTP; only `client.py`'s fetch/push functions are HTTP-specific. So `sync/file_sync.py` reuses all of the former and only adds folder export/import. A file record and an HTTP record are byte-identical and CANNOT drift. Lesson: when adding a transport, check whether the diff/serialize/insert layer is already pure (it should be, by the dependency rule) and reuse it; do not re-derive the merge logic for the new medium.
- **A folder snapshot is attacker-shaped input, exactly like a pushed record, so it inherits the SAME guards and needs one more.** A `*.memexsync.gz` in the shared folder could be crafted (or corrupt). `insert_record` already re-asserts the `max_chunks_per_conversation` cap + list-type guards + embedding-dim check (the sync path bypasses the pipeline), so the file path gets those for free. The NEW seam is decompression: a tiny gzip can inflate to GBs, so the line reader streams in fixed blocks and caps a single decompressed line (one record) at a flat 256 MB — above the largest legit single-conversation record (~57 MB at 5000 chunks), far below a bomb. Do NOT tie that cap to the 16 MB network body cap (I did at first): file sync has no per-request body limit, so a legit large record would be falsely rejected.
- **A bounded line reader that RAISES must be caught where it is consumed, or it crashes the whole sync.** `_iter_decompressed_lines` raises `ValueError` on an over-cap line; `_iter_records` is a generator that propagates it, and `import_once`'s `for record in _iter_records(...)` would have died on one bad peer file. Fixed by wrapping the per-file iteration so a read error aborts ONLY that snapshot (logged) and the other peer files still sync. Lesson: when a streaming guard can raise mid-iteration, the loop that drives the generator (not just the per-item body) needs the try/except.
- **Ownership-by-filename makes concurrent writers safe without locks.** Each device writes ONLY `<slug(device_name)>.memexsync.gz` and reads the others, so two devices never write the same file (and a dual-boot runs one OS at a time regardless). The export is an atomic temp-then-`os.replace`, so a reader on a synced folder never sees a half-written file. Convergence is pull-only per peer file + a full self-snapshot; the "push" half is emergent (the peer pulls my newer records on its next run). Give two devices DISTINCT `--device-name` values if their hostnames collide, or they overwrite each other's snapshot (documented; setup prints the chosen name).
- **Dual-boot has a hard filesystem asymmetry: the shared folder must live on the Windows/NTFS partition.** Linux reads/writes NTFS out of the box (ntfs-3g); Windows cannot read Linux's ext4 natively. So the only folder both OSes can reach is on the NTFS side. `memex setup --sync-dir` prints this. Unlike the Option A idea (one shared SQLite DB), file sync shares only a transport file, so it avoids all the SQLite-locking-over-a-mounted-filesystem problems.

### Persisted sync-reachable install: one flag the server reads, not a flag in every service template (2026-06-28)
- **When N service definitions (launchd/systemd/Scheduled Task, repo + wheel) all already run the SAME command, add the new behavior by having that command read a persisted flag, not by editing all N definitions.** The install redesign needed the autostart `serve` to come up sync-reachable. The instinct (and the handoff's fallback option) was to make each service def run `serve --sync` (or inject `MEMEX_SERVE_SYNC=1`), which means touching 5 templates including a repo shell wrapper. Instead `memex serve` reads the persisted `serve_sync` gate flag when no `--sync/--no-sync` is given, so ZERO service definitions change and there is one source of truth. The `--sync` flag stays as a manual override. Lesson: a persisted flag the running process reads scales better than threading a flag through every launcher.
- **Binding `0.0.0.0` is necessary for the unified serve (uvicorn binds ONE host), so the token is the real gate and the Host allow-list is defense in depth.** The always-on `serve` must answer BOTH loopback (the Chrome extension) and the Tailscale address (sync); uvicorn cannot bind two specific hosts, so sync mode binds `0.0.0.0`. That opens the port on every interface (incl. the LAN), so a LAN peer can TCP-connect and even spoof `Host: <tailscale-ip>` to pass `TrustedHostMiddleware`; the per-install token (constant-time) is what actually stops them. Keep the allow-list widening ONLY to loopback + the resolved Tailscale IP (never a wildcard, never drop loopback) and resolve it AT STARTUP (never bake the IP into a service def, so a Tailscale IP change is picked up on restart). The one-shot `memex sync serve` is stricter (binds the specific addr, not `0.0.0.0`) because it does not also serve the loopback extension. README states plainly what `--sync` exposes.

### Multi-device sync: deletes do not propagate; a fork is resolved by content completeness (2026-06-28)
- **Sync NEVER propagates a deletion. Deleting a conversation on one device alone is undone by the next reconcile** (the peer still has it -> `pull` brings it back; reconcile is presence + last-writer-wins, it has no tombstones). Found via `ram-iso-1`, a test fixture (0 messages / 13 chunks) that had leaked into the Mac's REAL `data/memex.db` and rode a `push` to Windows. To truly remove a conversation from a synced set, delete it on EVERY paired device before any reconcile, and via `repo.delete_chunks_for_conversation` (never a raw DELETE -> orphans vec/fts; see the data-integrity entry). Lesson 2: tests must write a TEMP DB, never `settings.db_path`; a fixture in the real store spreads to every paired device.
- **A "fork" (same `updated_at`, different content hash) is the same claude.ai chat captured with different COMPLETENESS on each device, so resolve it toward the more complete copy.** `reconcile` correctly refuses to auto-pick (LWW can't break a timestamp tie) and reports forks. To resolve: compare chunk/message counts per side, and if one device is `>=` on all forks, force that side with `memex sync push --peer <name>` (local wins) or `pull --peer <name>` (peer wins) -- the explicit hash-diff overrides exist exactly for this. In the live Mac<->Windows converge the Mac had `>=` chunks on all 10 forks (9 more, 1 tie), so `push` was lossless. Do NOT blindly force a side without checking counts; pick the side that does not shrink any conversation.
- **A single conversation bigger than the default 8 MB client budget needs `MEMEX_SYNC_MAX_BATCH_BYTES` raised on the SENDER, and the receiver's body cap (`MEMEX_INGEST_MAX_BODY_BYTES`, default 16 MB) must still admit it.** `_resolve_budget` = `min(local budget, 0.8 * peer cap)`, so the local 8 MB default is the binding limit even when the peer advertises 16 MB. Two oversized `claude_code` sessions (11.76 / 9.46 MB) only pushed at `MEMEX_SYNC_MAX_BATCH_BYTES=14000000` (-> a 12.8 MB budget). The skip-and-report is working as designed (the message even says which knob to turn); it is a per-item knob, not a bug.

### Multi-device sync: batch a vector-carrying payload by BYTES, not by item count (2026-06-27)
- **A request that carries embeddings must be batched by serialized size, never by a fixed item count.** `memex sync push`/`reconcile` batched conversations 500-at-a-time, bounded only by the server's `_MAX_SYNC_UUIDS` count cap. But each conversation ships its chunk vectors (~11 KB per chunk as JSON floats at dim 768), so a batch of a real history (the live re-test pushed 158 conversations / ~6 k chunks at once) far exceeded the receiver's 16 MB `ingest_max_body_bytes`. The server rejects an oversized body with 413, but `_read_body_capped` returns it (and closes) while urllib is still uploading, so the CLIENT sees a `Broken pipe`, NOT a clean 413, and the old CLI reported it as "could not reach peer" (a misleading message for what is really "body too big"). Fix: `_serialize_and_push` accumulates serialized records up to a byte budget and flushes before exceeding it; `_fetch_and_insert` does the same on the pull side using a per-record size ESTIMATE (the client has no local copy to measure, so it estimates from the manifest's `chunk_count` and dim). Lesson: the moment a sync/transfer payload includes vectors (or any per-item blob), a count-based batch is a latent body-cap bomb that only fires once a user has real data; budget by bytes from day one.
- **A self-describing wire protocol makes the size budget correct without guessing.** The client cannot know the peer's body cap, so `/sync/manifest` now advertises `max_body_bytes`; the client fills to 80% of it (`_resolve_budget`). A peer too old to advertise it (e.g. one still on `0.4.0`) falls back to the local 8 MB default, which is already under the 16 MB default server cap, so a NEW client still syncs with an OLD peer (verified live: the Mac pulled 161 conversations from a `0.4.0` Linux in 23 byte-bounded requests, 0 failed). Lesson: when a client must respect a server-side limit, have the server tell the client the limit (with a safe fallback for an older server) instead of hardcoding an assumption on the client.
- **A single item bigger than the cap must be skipped loudly, not retried into an abort.** One conversation whose own serialized size exceeds the budget can never fit in any request. The push path skips it with an ERROR log + an `oversized` count surfaced in the summary/CLI (raise `MEMEX_INGEST_MAX_BODY_BYTES` on the peer or lower `MEMEX_MAX_CHUNKS_PER_CONVERSATION` to move it), rather than sending it and dying on the broken pipe (which would abort the whole sync, since `_serialize_and_push` does not catch per-batch errors). Lesson: distinguish "batch too big" (fix by batching) from "one item too big" (cannot batch away; skip + report).
- **Operational gotcha (not a code bug): `memex serve --host <addr>` does NOT add `<addr>` to the Host allow-list.** `--host` is only the bind interface; `TrustedHostMiddleware` validates the `Host` header against `MEMEX_INGEST_ALLOWED_HOSTS` (default `127.0.0.1,localhost`) separately. The live re-test first failed with `Invalid host header` because the Tailscale IP was bound but not allow-listed. The peer must set `MEMEX_INGEST_ALLOWED_HOSTS` to include the address the other device dials. (Documented in the README sync section.)

### Multi-device sync Phase 3: gating + hardening the sync surface (2026-06-24)
- **A feature that adds a network surface needs an explicit master gate, off by default, distinct from "is it currently exposed."** Before Phase 3 the `/sync/*` endpoints answered to any token holder whenever `serve` was bound beyond loopback; "off by default" relied on the bind + no paired peer. Phase 3 adds a persisted `enabled` flag (`sync/state.py` -> `sync_state.json`) that the endpoints read PER REQUEST and 404 when off, so a user who never opts in has zero sync surface even if they bind `serve` to a LAN/Tailscale address for the extension. The gate returns **404, not 401/403**, so a disabled device does not even reveal the endpoint exists. Fail-closed: an unreadable/corrupt/half-written gate file reads as disabled.
- **Keep a frequently-written breadcrumb apart from a rarely-written gate, or the breadcrumb race-clobbers the gate.** The `enabled` flag is written only by `enable`/`disable`; the per-peer last-sync (time + counts, for `status`) is written on EVERY sync (auto-sync every tick + each manual run). Co-locating them in one JSON file would let an in-flight history write (which did read-modify-write of the whole file) reload a stale `enabled` and write it back, silently undoing a concurrent `enable`/`disable`. Two files (`sync_state.json` gate, `sync_history.json` breadcrumbs) means the gate is only ever touched by the toggle. State writes are also atomic (write a `pid`-suffixed temp then `os.replace`) so a concurrent reader never sees a partial file.
- **A second write path to the same tables inherits NONE of the ingest pipeline's guards; re-assert them.** `insert_record` (the sync insert path) writes conversations/messages/chunks directly through the repo, bypassing the pipeline, so it also bypassed `max_chunks_per_conversation` (the cap that bounds one conversation's embed/store fan-out). A compromised paired peer could push a record with an unbounded chunk count (only the request body cap bounded it). Added the chunk-count cap + list-type guards on `messages`/`chunks` in `insert_record`. Lesson: whenever a non-pipeline path inserts the same rows, copy the pipeline's bounds onto it.
- **A per-request COUNT cap on a sync endpoint must bound the response/insert MEMORY, not just the item count.** `/sync/conversations` materializes a FULL conversation (text + chunks + vectors) per requested uuid into one in-memory JSON response; the cap was 5000 while the client only ever batches 500 (`client._DEFAULT_BATCH`), so a token-holding (trusted-but-maybe-compromised) peer could ask for 5000 full conversations = hundreds of MB in a single call. Lowered `_MAX_SYNC_UUIDS` 5000 -> 1000 (2x the client batch). The body cap bounds a push's bytes; the count cap is the matching bound on a fetch's amplification.
- **Pairing is a FULL-TRUST relationship: LWW timestamps and redaction both assume an honest peer.** A paired peer holds your per-install token (the SAME one `/ingest` uses), so it can also POST `/ingest`; reconcile trusts the peer's `updated_at` for last-writer-wins (a peer claiming a far-future timestamp can overwrite any of your conversations); and the receiver does not re-redact a pushed record (the vectors already encode the text, and re-chunking would break the no-re-embed design), so a malicious peer could push unredacted content. All within the "only pair devices you control" boundary; the threat-model detail is in `docs/internal/security-notes.md`. Lesson: a P2P sync's integrity is only as strong as the pairing decision; do not claim "no unredacted secret crosses the wire" without the honest-peer caveat.

### Multi-device sync Phase 2: bidirectional sync needs last-writer-wins, not hash-diff (2026-06-24)
- **A naive two-way reconcile by content hash silently overwrites the newer copy with the older one.** Phase 1's pull fetches whenever the content hash differs (one-directional: the source is authoritative, so "take its version" is the intent). Reusing that for a bidirectional reconcile is a data-loss bug: the same claude.ai chat captured on both devices at different times has two hashes, and a hash-only diff would pull the peer's OLDER copy over the local NEWER one (and vice versa), depending on direction. The plan defers full conflict policy to Phase 3, but the minimum needed for a SAFE bidirectional v1 is last-writer-wins by `updated_at`: pull only where the peer is newer-or-absent, push only where local is newer-or-absent, skip equal, and leave a same-timestamp-different-content fork untouched (never overwrite). `select_reconcile` does this; the explicit `pull`/`push` commands stay hash-diff one-directional overrides because there the user picks the authoritative side on purpose. Lesson: a diff rule that is correct for one-directional sync is not automatically correct bidirectionally; add a freshness tiebreaker before syncing both ways.
- **Auto-sync must take the single-flight ingest lock NON-BLOCKING and skip if busy, not block on it.** The auto-reconcile runs inside the always-on `serve` process. Sync does not load the embedding model (vectors travel), so the lock is not for RAM; it is to keep a sync write from contending with an in-flight ingest. But holding it blocking for a whole reconcile (HTTP + many inserts) would make a concurrent live capture wait up to the 60s lock timeout and then 503. So the auto-sync tick acquires `ingest_lock.acquire_nonblocking` and skips the whole tick if an ingest holds it (the next interval retries); it never blocks a capture. The manual `memex sync` commands take no lock (user-initiated, immediate). The lifespan task also uses its OWN short-lived DB connection, never the server's event-loop-bound `_conn` (the `_get_conn` comment warns that a background task touching that connection must be serialized).

### Multi-device sync Phase 1: inserting a record must satisfy every FK (2026-06-24)
- **A synced `design_chat` carries a `project_uuid` foreign key; inserting it on a device that lacks the project fails the FK.** `conversations.project_uuid REFERENCES projects(uuid)` is enforced (`PRAGMA foreign_keys` is ON per connection), so `insert_conversation` for a project chat raises `IntegrityError FOREIGN KEY constraint failed` on a receiver that never had that project. Reproduced before fixing. Fix: the source ships the Project row inside the `/sync/conversations` record and the client upserts it before the conversation; if a peer omits it (older peer, dangling ref), the client drops the project link rather than failing the whole insert. Lesson: when transferring a row to another DB, transfer (or null) everything its foreign keys depend on; never assume the receiver's reference tables match the sender's.
- **Chunk ids are local AUTOINCREMENT, so a synced conversation must get NEW local chunk ids, not the peer's.** The insert path goes through `delete_chunks_for_conversation` + `add_chunk(chunk_with_id_None, embedding)`, so the receiver assigns its own ids (and keeps `vec_chunks`/`fts_chunks` in sync). Reusing the peer's chunk ids would collide with a different local chunk. The vectors travel and are re-inserted as-is (no re-embed); only the ids are reassigned.
- **The sync endpoints must NOT require the extension Origin** (a peer is not a browser and will not send `chrome-extension://`). They are token-gated only (constant-time compare), with the Host still pinned by `TrustedHostMiddleware`. This is the opposite of `/ingest/*`, which require BOTH. Do not copy the `/ingest` auth wholesale onto a machine-to-machine endpoint.

### Ingest RAM — the embedding model is the floor; serialize every loader (2026-06-23)
- **The transient ingest RAM peak (~0.69 GB) is the embedding model load, not a tunable.** Measured on `nomic-embed-text-v1.5-Q` at batch=1/threads=1 (already the minimum): peak RSS is ~0.45 GB just to load the model + onnxruntime runtime, ~0.085 GB of inference activations (the only part batch/chunk-size touch), and ~0.13 GB of memex process overhead (pipeline + sqlite + redact). The two big levers were already pulled (batch and threads at 1). Things that DON'T help: `enable_cpu_mem_arena=False` (fastembed exposes it, but measured 538 vs 545 MB, pure noise); a multilingual small model (e.g. `paraphrase-multilingual-MiniLM-L12-v2`) uses MORE RAM (~0.88 GB) because its vocab embedding table is huge. The only real RAM cut is a smaller English model (`all-MiniLM-L6-v2` ~0.26 GB) but it measurably degrades Spanish recall (4/6 vs nomic 6/6 on a semantic test), so it is NOT a free win for a Spanish+English corpus. Lesson: do not chase the per-worker peak with config; it is near the floor for a quality multilingual embedder. Lower `MEMEX_CHUNK_SIZE` (500 -> ~256) only shaves ~85 MB and needs a re-index for consistency.
- **Every code path that loads the embedder must share one single-flight lock, or two ~0.5 GB loads stack.** The `ingest-claude-code` CLI (manual / 15-min schedule / SessionEnd hook) already took a non-blocking `ingest.lock`, but the live-capture worker (`http_ingest` -> `ingest_worker` subprocess) did NOT, and `http_ingest` awaits each subprocess so concurrent POSTs (a backfill burst, several claude.ai tabs) could each spawn a worker. So capture-vs-capture AND capture-vs-CLI could double/triple the peak. Fix: extracted the lock to `memex.ingest_lock` (shared by both) and added two fronts in `_ingest_in_subprocess` — an in-process `asyncio.Lock` serializes the server's own workers, and the cross-process `ingest.lock` is taken blocking-with-timeout (60s) so a live capture WAITS for an in-flight ingest instead of stacking, then drops to a 503 (extension re-sends / backfill self-heals) rather than ever loading a second model. CLI keeps the non-blocking skip (the schedule re-runs in 15 min). Lesson: when N independent triggers can each load a heavy model, a per-path lock is not enough; they must serialize on ONE cross-process lock, and the right wait policy differs per caller (skip for a periodic backstop, wait for fresh user data).

### Phase B install — Windows wheel autostart (2026-06-20)
- **A Windows background task uses `pythonw.exe`, where `sys.stdout`/`sys.stderr` are `None`.** The wheel-mode logon Scheduled Task runs `pythonw -m memex.cli.main serve` (no console window). `serve` printed via rich and checked `sys.stdout.isatty()`, both of which raise on `None`, so the server crashed before binding 5777 (the task fired, nothing listened). `memex serve` worked by hand because a real console has valid streams; the task did not. Fix (0.3.1): `_redirect_streams_if_headless()` reopens the streams to `serve.log` in the data dir when they are `None`, and `isatty()` is `None`-guarded. Lesson: any CLI entry point that a Windows task (or `pythonw`) might run must tolerate `None` std streams; do not assume `sys.stdout` exists. The token print stays gated on a real tty, so a file-backed stream still will not log it.
- **A published PyPI version can never be re-uploaded.** 0.3.0 went up before this Windows bug was found, so the fix shipped as 0.3.1. Test the wheel locally (`pipx install ./dist/*.whl`) before publishing when feasible.

### Phase B install — Linux one-liner ran under dash (2026-06-22)
- **A `curl ... | sh` installer runs under the system `/bin/sh`, not its shebang.** `install-pypi.sh` declared `#!/usr/bin/env bash` and used `set -euo pipefail`, but the documented one-liner pipes it to `sh`. On Debian/Ubuntu `/bin/sh` is `dash`, which has no `pipefail`, so the first live Linux run died immediately with `sh: 14: set: Illegal option -o pipefail`. It passed on macOS only because there `/bin/sh` IS bash. Fix: make the script genuinely POSIX (`#!/bin/sh`, `set -eu`, no `pipefail`); the failed-pipe case it guarded is already caught by the `command -v uv` check. Lesson: any script invoked as `curl | sh` must be POSIX sh, not bash; test it with `dash -n` (and `dash` is installable on macOS to reproduce). The other repo scripts are unaffected because they run via their shebang or an explicit `bash` (`_run_install_service` calls `install-autostart.sh` as `subprocess.run([bash, ...])`); only the `| sh`-documented script had the latent bug. The script is served from GitHub raw `main`, not the wheel, so a push fixes the live one-liner with no PyPI re-publish.

### Phase 7 + Phase B close audit (2026-06-22)
A five-dimension audit at the phase boundary; findings fixed (523 tests green). The auth gate held (Origin+token, constant-time compare, 0600 token, TTY-gated print); all findings were media/baja. Lessons (fixed, do not repeat):
- **A systemd unit is line-oriented with no escape for a newline.** Never interpolate an attacker-influenceable path (`MEMEX_DB_PATH`, `$HOME`) raw into a unit: a `\n` injects a new directive (e.g. an `ExecStartPre=` that runs at login), a `"` breaks the quoted `Environment=`. `render_systemd_unit` now rejects newline/quote in the path (`_systemd_safe_path`). Give daemon units `UMask=0077` (the launchd plists had it, the wheel systemd unit did not, so its log was world-readable 0644), and create any daemon log (`serve.log`) 0600.
- **A request-body byte cap does not bound per-item work.** `/ingest/plan` took an unbounded `conversations` list; 16 MB of tiny objects is ~1M items, each forcing a full-table scan rebuild + timestamp parses on the event loop. Cap the list length (50k) for any local endpoint that loops a caller-supplied list, even behind the token.
- **A short-lived worker subprocess must not inherit the parent's full `os.environ`.** Strip secrets it never uses (`ANTHROPIC_API_KEY`, `MEMEX_GITHUB_CLIENT_SECRET`) so they are not in the child's `/proc/<pid>/environ`.
- **Never return a subprocess's stderr to the client.** The ingest worker's stderr can carry the absolute DB path; log it server-side and return only the return code.
- **pydantic-settings `populate_by_name=True` also reads each field's bare snake_case name from the environment** (`db_path`, `anthropic_api_key`, `ingest_allowed_hosts`), not only the declared `MEMEX_*`/standard alias. A generic inherited env var could relocate the DB or weaken a security setting. Removed it; tests construct `Settings` by alias. Same family as the earlier "env > `.env` shadows a reloaded setting" lesson.
- **A serving wrapper's default can silently drift from the pure function's.** The `get_chat` MCP wrapper defaulted `messages_limit=20` while the tool (and the docstring) used 10; reference the shared constant so the served default cannot diverge.
- **Report install failures in the exit code.** macOS `install-service` returned 0 even when a launchd load printed FAILED (the Windows branch did inspect for it); now it returns non-zero like Windows.

The one live residual (the extension's page-world backfill reply channel is forgeable, integrity-only, cannot be closed in MAIN world) is in `docs/internal/security-notes.md`, not here.

### Phase 7 backfill (2026-06-19)
- **A cross-origin `fetch` from the extension may DROP the `Origin` header on GET, but POST keeps it.** The incremental-backfill endpoint started as `GET /ingest/known`; the background service worker's GET to `127.0.0.1:5777` did not carry the `chrome-extension://` Origin, so `_origin_allowed` returned 403 and the backfill silently fell back to fetching everything. The working `POST /ingest/conversation` path always sends the Origin. Fix: make the endpoint `POST /ingest/plan` (it also lets the server do the filter and keeps the indexed set server-side). Lesson: any new extension->server endpoint that relies on the Origin check must be a POST, or it must not depend on Origin.
- **Comparing claude.ai timestamps needs instant comparison, not string equality.** The ingest normalizes fractional seconds (`...000Z` -> `...000000Z`), so the stored `updated_at` is not byte-identical to the value claude.ai's list returns even when the chat is unchanged. Compare by parsed instant (`datetime.fromisoformat` server-side / `Date.getTime()` in JS), treating unparseable as oldest so the conversation is re-fetched (fail safe toward completeness).
- **`launchctl kickstart -k com.memex.serve` mid-ingest SIGTERMs (-15) the in-flight ingest subprocesses.** During backfill testing, restarting the capture server to load new code killed ~13 in-flight embed workers; the extension recorded them as `http-503 ingest worker exited -15`. No data loss (SQLite WAL rolls back a killed write, the killed ones were re-ingests of already-stored chats, and the incremental self-heals missing ones on the next run), but do NOT restart `memex serve` during a bulk ingest. The `model has been updated` text in those errors is an incidental fastembed stderr warning, not the cause.

### Red-team round 4 (data-theft focus, 2026-06-12)
- **A digest carve-out must require ADJACENCY, never a free-text word on the line.** `_DIGEST_CONTEXT` matched bare words (`object`/`commit`/`hash`/`tree`/`oid`) anywhere in the look-back window, so `the commit message references <64-hex>` exempted a 256-bit key. Real digest lines abut the marker (`sha256:HEX`, `commit HEX`, `etag: "HEX"`); anchor the marker to the end of the preceding slice (`...[\s:=@"'()-]{0,4}$`). Same lesson as the round-3 `_INTEGRITY_PREFIX` fix, applied to the hex64 path that round 3 missed. Any future "this looks like a hash/path, skip it" carve-out: gate on adjacency, because an attacker controls free text and will prepend the exempting word.
- **The high-entropy pass judges each separator-split segment alone, so dot/colon-chunked secrets evade it.** A Discord `id.ts.hmac` or Telegram `id:secret` (or any deliberately chunked token) has every piece under the 28-char floor → zero matches. Fix needs a rule that evaluates the JOINED run, gated hard to avoid eating dotted domains/semvers/package-coords/code-paths: concatenated body ≥40 chars, all three character classes, entropy ≥4.0, not a camel identifier, AND `/` EXCLUDED from the segment charset (else the run bridges across path slashes and swallows `/Users/.../foo.whl`, the exact bug that failed a MUST_PRESERVE test on first cut).
- **Strip Unicode format chars (Cf + TAG block) at INGEST, not only at read time.** A zero-width space / soft hyphen / bidi control inserted mid-secret splits the token so each half falls under the floor and survives. The read-time `_sanitize_untrusted` strip is too late: the split token is already chunked and embedded. Call the strip first thing in `redact_secrets`.
- **Require a newline after a multiline block's header or a packed unterminated run is a ReDoS.** `-----BEGIN ... PRIVATE KEY-----` repeated with no newline/END forced the lazy `[\s\S]{0,16384}?` body to scan 16 KB per marker → O(n*16384), ~10 s on 2.9 MB. Requiring `[ \t]*\r?\n` after the header makes a junk BEGIN fail instantly. Real PEM/armored blocks always newline after the header, so they are unaffected (verified incl. CRLF).
- **Name EVERY surfaced field in the untrusted-content envelope.** `get_chat` returns a Claude.ai Project `description`/`prompt_template` (a prompt_template reads like a system prompt), but the note only listed title/summary/snippet/message text. Enumerate the project fields too so the consuming model does not treat the highest-authority-looking field as trusted config. Audit the note whenever a tool starts returning a new field.
- **Chrome extension `content.js` validates message origin + payload shape** before forwarding a capture; do not loosen it. The MAIN-vs-ISOLATED-world trust limit and why a nonce handshake does not close it are recorded in `docs/internal/security-notes.md` (it is a residual integrity limit, not exfiltration).
- **Two live, documented-not-fixed limitations** (the unauthenticated DCR `/register` disk-exhaustion DoS, and the extension page-world poisoning vector) are detailed in `docs/internal/security-notes.md`, not here, since they point at still-open soft spots. Read that file before touching the remote connector or the capture path.

### Data integrity: never raw-DELETE conversations (orphans vec/fts) (2026-06-12)
- **Deleting from `conversations` (or `chunks`) directly orphans `vec_chunks` and `fts_chunks`.** Those are virtual tables (sqlite-vec / FTS5) and do NOT participate in the FK `ON DELETE CASCADE` that links messages/chunks to conversations. A raw `DELETE FROM conversations WHERE source='claude_code'` cascades to `chunks` but leaves their vector + FTS rows behind. Found during a redaction re-index: the DB carried 3823 orphaned vec/fts entries (vec=fts=7355 vs chunks=3532), almost certainly from a prior session that cleared rows with a raw delete. Orphans waste space and degrade KNN search (it returns vec rowids that no longer join to a chunk). AUTOINCREMENT means ids are never reused, so it does not mis-map, just drops results.
- **Always go through `repo.delete_chunks_for_conversation()`** (which deletes vec + fts + chunks together) before/instead of touching those tables. The ingest pipeline already does this on re-ingest, so re-ingesting is safe; only out-of-band deletes are dangerous. To re-index with new redaction WITHOUT deleting: set `content_hash=NULL` on the target conversations and re-run `ingest-claude-code` (the skip-unchanged check fails, the pipeline cleanly replaces chunks). To clean existing orphans: `DELETE FROM vec_chunks/fts_chunks WHERE rowid NOT IN (SELECT id FROM chunks)` (batch the rowids). There is no `delete_conversation` helper yet; if one is added, it MUST call `delete_chunks_for_conversation` first.

### Remote transport / claude.ai connectors (Phase 4, 2026-06-11)
- **claude.ai connectors cannot use a pasted token or custom header.** The only auth schemes its UI accepts are *authless* or *full OAuth 2.0 with dynamic client registration* (PKCE S256). The ROADMAP's original "local token in header" idea was impossible for this client. If you ever re-touch remote auth, do not reach for a bearer/header scheme: it will not connect.
- **The connection originates from Anthropic's cloud, never from the user's device.** So the server MUST be on a public HTTPS URL with a public IPv4 `A` record; `localhost`/private IPs are rejected at DNS validation. A tunnel (Tailscale Funnel) is mandatory, not optional. The user's machine must be on and the tunnel up for the connector to respond.
- **Allow-list must be enforced on every request and fail closed.** `AllowlistGitHubProvider.verify_token` (`transports/http.py`) re-checks the GitHub identity on each call (token-result caching is disabled by default in fastmcp's `GitHubTokenVerifier`, so revocation is immediate). `build_remote_app` refuses to start with an empty allow-list. Never add a code path that builds the remote server with `auth=None`; the only legitimately authless server is local stdio.
- **Match the immutable numeric id (`sub`), not just the username (`login`).** GitHub usernames are reusable after an account is deleted/renamed, so a username-only allow-list means a renamed/reused handle could grant access to the whole corpus. The allow-list now accepts either form (security audit LOW-1). The `login` claim itself is trustworthy (set live from `api.github.com/user`, keyed by the server-held token, not client-controllable) so it is fine to match on; the `sub` option is the stronger pin.
- **Test pitfall: do not patch via `Class.__mro__[1]`.** A fastmcp version bump can reorder the MRO and silently change what gets patched. Patch the method on the class where it is defined (e.g. `GitHubProvider.verify_token`), which `super()` resolves to regardless of intermediate classes.

### Claude Code ingestion + CHECK migration (Phase 6, 2026-06-11)
- **`PRAGMA foreign_keys` is a no-op inside a transaction.** The `conversations.source` CHECK migration (recreate-table to widen the allowed values) toggles `foreign_keys = OFF` so the `DROP TABLE` does not cascade. The first cut toggled it while an implicit transaction was still open, so FKs stayed ON and the swap failed with "no such table" against a forward-referenced parent. Fix: `conn.commit()` before the toggle. Verify with `PRAGMA foreign_keys` returning 0 if ever in doubt.
- **SQLite cannot ALTER a CHECK constraint in place.** Adding a new `source` value means recreating the table (the 12-step procedure). Copy columns by intersection of old and new, not `SELECT *`, so a DB predating a column (`ingested_at`, `content_hash`) still migrates. Always make it idempotent by checking the live DDL (`sqlite_master.sql`) for the new value first.
- **Reuse the renderer's unknown-block behavior on purpose.** `content_renderer` ignores unknown block types, so assistant `thinking` blocks are dropped for free without special-casing. When adding a new transcript format, lean on that instead of writing a second renderer.

### Security audit lessons (final sweep, 2026-06-11)
- **Bound every quantifier in redaction regexes.** A greedy `[...]*://` prefix made `url-credentials` O(n²) on a long whitespace-free blob (~6 s on 180 KB), and redaction runs on every captured session. Terminal/file capture routinely contains minified JS / base64 / long log lines, so unbounded patterns are a real DoS, not theoretical. Use `{0,N}` everywhere and add a large-blob timing regression test.
- **Redaction is best-effort; pair pattern rules with a high-entropy fallback.** Prefix-only rules miss random secrets with no known shape. A Shannon-entropy fallback (skip pure-hex/UUIDs and oversized base64 to avoid mangling) catches the rest. Redact BEFORE truncation so a secret straddling the cut is masked whole.
- **Never echo a secret to a stream that a daemon redirects to a file.** `memex serve` printed the ingest token at INFO; under launchd that went to a world-readable `data/serve.log`. Gate secret prints behind `sys.stdout.isatty()`, set `umask 077` in daemon scripts, and `Umask` (077) in the launchd plists (launchd creates `StandardOutPath` logs 0644 otherwise).
- **A config-time allow-list does not revoke until restart.** `AllowlistGitHubProvider` captured the allow-list once at construction; with a persistent daemon, removing a login had no effect until a manual restart. Re-read it on `.env` mtime change (fail-safe to the last good, non-empty set). GitHub-side token revocation was already immediate (token caching is off).
- **Put `TrustedHostMiddleware` outermost.** FastMCP appends user middleware after its auth backend, so a TrustedHost passed to `http_app(middleware=...)` runs AFTER auth — meaning a bad-Host request still triggers the per-request GitHub API call. Use `app.add_middleware(...)` (prepends) so Host is validated first.

### GitHub push protection blocks realistic-looking test secrets (2026-06-11)
- **Do not commit literal secrets that match a known provider shape, even fake ones.** GitHub secret-scanning push protection (GH013) rejected a push because `test_redact_adversarial.py` contained a Twilio Account SID (`AC` + 32 hex) and a New Relic key (`NRAK-...`) — they were fake test vectors, but the scanner matches by shape. Same risk for AWS `AKIA`, GitLab `glpat-`, Google `AIza`, SendGrid `SG.`, Stripe, `sk-ant-`, `ghp_`, etc.
- **Fix: build vendor-shaped test secrets from adjacent string fragments** so no complete literal exists in the file (Python concatenates `"AC" "1234..."` at parse time; the scanner sees two separated literals). The runtime value is still the full secret, so the redaction test stays valid. Keep this in mind for ANY test/fixture that needs realistic credentials.

### Red-team rounds on redaction (2026-06-11)
- **A config-time setting reloaded from `Settings()` is shadowed by an OS env var.** pydantic-settings precedence is env > `.env`, so re-reading the allow-list via `get_settings()` on `.env` change is a silent no-op if the var is also exported. Read the watched file DIRECTLY for the one setting that must be live, and warn if the env var is set. Use `(st_mtime_ns, st_size)` as the change signal, not bare `mtime`.
- **Redaction false positives matter as much as false negatives.** Over-redaction (masking file paths, git/integrity hashes, object-store keys) destroys the search the index exists for. Keep `/` OUT of the high-entropy token charset (so paths split per segment), skip a token right after `/` (path/URL segment) or after a digest marker (`integrity`, `sha256-`), skip pure-hex (git SHAs) and route 64-hex keys through a dedicated rule that excludes digest contexts. Keep a MUST_PRESERVE corpus alongside MUST_REDACT.
- **The entropy fallback can never catch pure-hex.** Max Shannon entropy of a 16-symbol alphabet is 4.0, so a 64-hex key never clears a `>= 4.0` gate. Hex secrets need a dedicated length-based rule, gated on NOT being a digest context, not the entropy path.
- **Bounded upper quantifier prevents a cleartext tail.** A `{32,100}` token candidate masks a >100-char secret in 100-char chunks and leaves the 1–31-char remainder verbatim. Use a generous upper bound (`{28,4096}`) so the whole run is one match.
- **Consent screen is the confused-deputy defense.** With DCR + `allowed_client_redirect_uris=None`, only the consent-binding cookie stops a malicious-redirect token theft. Never set `require_authorization_consent=False`; a regression test asserts it stays enabled. Immediate revocation also depends on `cache_ttl_seconds` staying unset (token cache off).

### Red-team round 2 (2026-06-11)
- **Redaction was only on message text — the TITLE bypassed it.** When a field is derived from ingested content (a model-generated `aiTitle`, a cwd-based fallback) and stored/surfaced, it must go through the same redactor; otherwise it leaks via search, get_chat, AND the summarizer (which forwards the title to the Anthropic API and re-stores it). Audit every derived/stored field, not just the obvious body.
- **A per-token line back-scan is O(n^2) on a single long line.** `_line_before` doing `rfind("\n")` per candidate is fine with newlines but quadratic on a minified/one-line blob (11 s on 199 KB). Bound the look-back to a fixed window; context markers sit right before the token so it is equivalent.
- **Removing `/` from the entropy charset (to protect paths) lets base64-with-`/` secrets through.** The AWS secret key (40 b64 chars, often has `/`) needs a dedicated rule, gated on mixed character classes (a path segment is single-case) and not-preceded-by-`/`.
- **Entropy thresholds must be length-tiered, not flat.** Long alpha-only code identifiers (PascalCase, 40+ chars) sit at entropy ~4.0-4.4 and collide with the 4.0 floor; raising the floor flatly would leak 32-char alpha secrets (same entropy). Tier it: higher floor only for the long band.
- **`.env` parsing: match the exact key with an `=` boundary.** `startswith("KEY")` also matches `KEY_OLD=evil` and can hijack the value. Use `partition("=")` + exact compare, take the last assignment (dotenv semantics), strip `export ` and inline comments.
- **Strip Unicode bidi/zero-width controls from tool output.** They let an attacker visually disguise injected instructions in stored chat text. A recursive strip in the result serializer is cheap and a no-op for dates/uuids.
- **`resolve_repo_key` must match the `repos.path` column, not just the key.** A repo with a git remote is keyed by the remote URL (`canonical_repo_key` prefers it), so resolving a filesystem path (a session `cwd`, or a user-passed `--repo` path) by key alone silently returns `None` for every cloned-from-GitHub repo. The Phase 6 cwd→repo association shipped broken because of this and a test that only covered `remote_url=None`. When a feature resolves a path to a registered repo, cover the git-remote-keyed case explicitly.
- **Indexing terminal/file capture widens the remote blast radius; redact secrets.** Claude Code sessions contain command output and file contents with real credentials, and the remote claude.ai connector can surface that indexed text. `core/ingest/redact.py` masks common secret shapes on the `claude_code` path before storage/embedding, and `raw_content` is not persisted for that source. Any future source that ingests machine/terminal capture (not genuine conversation) must run through redaction too. The `_meta.untrusted_content` injection envelope is source-agnostic, so new sources inherit it for free.

### Resource audit round 3 (2026-06-11)
- **fastembed `parallel=1` is NOT single-process.** Only `parallel=None` runs inference inline. Any non-None value (with a batch ≥ `batch_size`) takes the worker-pool branch (`onnx_text_model._embed_documents`), which spawns a subprocess that loads its own model copy AND is re-spawned on every `embed()` call. The fix for the RAM blowup is `parallel=None`, not `parallel=1`. A non-import-safe caller (no `if __name__ == "__main__"`) additionally crashes with a forkserver bootstrap RuntimeError. Never reach for `parallel=1` to mean "one process".
- **The embedding memory driver is the onnxruntime per-batch arena, not the model or the pipeline.** It scales with `batch_size * sequence_length`. At 500-token chunks: ~1.0 GB (batch=2), ~1.6 GB (batch=4), ~2.4 GB (batch=8). To bound RAM, lower `MEMEX_EMBED_BATCH_SIZE`, not the model. The pipeline's full_text + chunks + vectors for a 16 MB session total ~55 MB, so it is never the cause of a GB-level spike.
- **A windowed back-scan must clamp the search bound, not just the returned slice.** `_line_before` was still `rfind("\n", 0, pos)` (search from 0) after round 2 only clamped `text[start:pos]`. `rfind` scans its whole `[start, end)` range, so searching from 0 on a newline-free line is O(pos) per call and O(n^2) over many same-line tokens (a 2 MB single-line 64-hex blob took 9 s). Pass the window as the search start: `rfind("\n", pos - WINDOW, pos)`. The earlier round-2 regression test used alphanumeric tokens (high-entropy path, few matches) and missed the hex64 path entirely; cover the hex64 single-line case explicitly.
